# 打造零掉线的高可用网络：Clash Fallback故障漂移策略组实操指南

::: tip 💡 核心结论与技术速查
- **Fallback 本质**：`fallback` 是 Clash 规则引擎中专为“高可用容灾（High Availability）”设计的策略组类型。它严格按照你定义的列表顺序，**平时 100% 只走第一个主力节点**；只有当主力节点发生连续超时（宕机或断纤）时，**系统在数秒内自动将后续流量切换至第二个备用节点**。
- **与 url-test 区别**：`url-test` 是哪个节点延迟低就频繁跳去哪个，极易导致 IP 频繁变动而触发网站登录态失效（掉 Cookie）；而 `fallback` **只要主力活着就绝不乱跳**，稳定性极高！
- **主备黄金搭档**：第一顺位放月付的千兆专线（如 [光速云](/brands/guangsu)），第二顺位放不限时备用流量包（如 [星岛梦](/brands/xingdaomeng)）。
:::

## 一、高可用容灾网络架构设计

对于关键外贸订单沟通、线上股票交易或跨国视频会议，单点网络中断会带来无法估量的损失：

```
Fallback 自动化故障漂移与恢复时序图：
[应用程序发起连接]
         │
         ▼
┌────────────────────────────────────────────────────────┐
│ 策略组：🛡️ 高可用容灾通道 (type: fallback)              │
│ 探针健康巡检：每 30 秒向 Google 204 发起握手探测          │
├────────────────────────────────────────────────────────┤
│ 1. 状态正常时：100% 走【光速云 香港专线】 (主力高速)      │
│ 2. 主力突发故障超时：5秒内自动漂移至【星岛梦 不限时备用】 │
│ 3. 主力节点修复恢复正常：自动无缝回切至【光速云 香港专线】│
└────────────────────────────────────────────────────────┘
```

## 二、Clash 生产级 Fallback 策略组配置实战

在你的 Clash Verge Rev 或外部配置文件中，将 `proxy-groups` 修改或追加如下代码：

```yaml
proxy-groups:
  # 1. 核心高可用容灾策略组
  - name: 🛡️ 高可用自动容灾
    type: fallback
    url: http://www.gstatic.com/generate_204  # 全球公认探针地址
    interval: 30                             # 每 30 秒执行一次可用性探测
    timeout: 3000                            # 超过 3000ms (3秒) 判定为故障
    proxies:
      - 🚀 主力：光速云 香港专线01
      - 🚀 主力：光速云 日本专线01
      - ⚓ 备用：星岛梦 不限时专线
      - ⚓ 备用：微风网络 极速专线

# 2. 将重要业务绑定至容灾组
rules:
  # 关键生产力服务走容灾通道
  - DOMAIN-SUFFIX,google.com,🛡️ 高可用自动容灾
  - DOMAIN-SUFFIX,github.com,🛡️ 高可用自动容灾
  - DOMAIN-SUFFIX,stripe.com,🛡️ 高可用自动容灾
  - DOMAIN-SUFFIX,openai.com,🛡️ 高可用自动容灾
  - MATCH,🛡️ 高可用自动容灾
```

## 三、三步验证容灾是否生效

1. 打开客户端的“连接 (Connections)”监控面板；
2. 正常刷新 `google.com`，确认连接走的是第一个“光速云香港专线”；
3. **模拟故障测试**：在本地防火墙或将该节点伪造为不可达，等待 30 秒；
4. 再次刷新网页，观察连接是否已被系统自动秒级切换至第二个备用节点。如果网页依然能够正常打开，说明你的高可用网络已正式构建成功！
